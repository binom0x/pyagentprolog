## 1. Что это и зачем

Стандартный Prolog использует **строгую унификацию**: два атома совпадают, только если их строковые представления идентичны. Это даёт предсказуемое, но очень «жёсткое» поведение:

```prolog
?- столица(россия, X).
X = москва.
?- столица(россия, 'Москва').    % другой регистр
false.
?- столица(россия, 'Москве').    % другой падеж
false.
?- столица(россия, 'Moscow').    % другой язык
false.
```

**Семантическая унификация** — это надстройка над строгой унификацией, которая позволяет двум атомам совпасть, если они **близки по смыслу или написанию**. Она полезна, когда:

- запросы приходят от пользователя в свободной форме (чат, голос, естественный язык);
- база знаний содержит термины, которые пользователь пишет с ошибками, в другом регистре, падеже или на другом языке;
- нужно сопоставить термины без жёсткого словаря синонимов.

Семантическая унификация **не заменяет** строгую. Она включается **по запросу** (директива `:- semantic_on.` или вызов `semantic_on()` из Python) и **никогда не ломает** существующее поведение: если её выключить, всё работает как раньше.

### Что она ловит

| Тип различия | Пример | Обрабатывается |
|---|---|---|
| Регистр | `Москва` ↔ `москва` | Layer 1 (нормализация) |
| Кавычки | `'Париж'` ↔ `париж` | Layer 1 |
| Опечатки | `Масква` ↔ `москва` | Layer 2a (Levenshtein) |
| Морфология | `Москве` ↔ `москва` | Layer 2a |
| Кросс-язык | `Moscow` ↔ `москва` | Layer 3 (эмбеддинги) |
| Синонимы | `Moscow` ↔ `москва` | Layer 3 |
| Аббревиатуры | `РФ` ↔ `россия` | **НЕ обрабатывается** (см. §12) |

### Что она не ловит и не должна ловить

- **Факты о мире** (`РФ = россия`, `США = соединённые_штаты`). Это знание, а не близость текста. Решается **глоссарием на уровне Prolog** (см. §12).
- **Разные понятия, похожие по смыслу** (`кошка` vs `собака`). Они должны быть далеки, и это правильно.

## 2. Архитектура

Семантическая унификация встроена в `prolog/embedding_unify.py`. Точка интеграции — подключаемый унификатор в `prolog/terms.py`:

```
┌────────────────────────────────────────────────────────────────┐
│  Term.unify(other, subst, depth, occurs_check)                 │
│         │                                                      │
│         ├─── custom_unifier установлен?                        │
│         │                                                      │
│         └─── ДА ──► EmbeddingUnifier.unify(...)                │
│                       │                                        │
│                       ├─ разрешение переменных                 │
│                       ├─ строгая унификация (быстрый путь)     │
│                       ├─ рекурсия по составным термам          │
│                       └─ Layer 1 / 2a / 2b / 3                 │
│                                                                │
│         └─── НЕТ ─► Term.unify_strict(...)  (старое поведение) │
└────────────────────────────────────────────────────────────────┘
```

**Ключевые свойства:**

- **Неинвазивность.** `interpreter.py`, `parser.py`, `predicates.py`, `solver.py` ничего не знают о семантике. Они вызывают `Term.unify(...)`, и всё работает автоматически.
- **Отключаемость.** `semantic_off()` возвращает строгое поведение.
- **Thread-safety.** Кэш и состояние защищены `RLock`, флаг реентерабельности — через `threading.local`.
- **Никаких глобальных сайд-эффектов при импорте.** `embedding_unify.py` не трогает `terms._custom_unifier`, пока не вызовут `semantic_on()`.

## 3. Три слоя сопоставления

Когда `EmbeddingUnifier.unify(t1, t2, subst)` вызывается для пары атомов (0-арных термов), выполняется следующая последовательность. Слои упорядочены по возрастанию стоимости — от самого дешёвого к самому дорогому.

### Шаг 0. Разрешение переменных

Если `t1` или `t2` — переменная, связанная в `subst`, она разыменовывается. Это нужно, чтобы семантика работала, когда переменная уже связана с атомом:

```prolog
страна_по_столице(X, 'Токио')  % в правиле столица(япония, токио)
```

Переменная `Y` внутри `страна_по_столице` уже связана с `'Токио'`, но в правиле сравнивается с `токио`. Без разрешения был бы «случай переменной» и строгая унификация отвергла бы пару. С разрешением — сравнение идёт `'Токио' vs токио`, и семантика срабатывает.

**Если хотя бы одна сторона — несвязанная переменная**: вызывается строгая унификация, семантика не применяется. Переменные нужно связывать, а не «сравнивать по смыслу».

### Шаг 1. Layer 1 — точное совпадение после нормализации

`_normalize_text(s)`:
1. `strip()` — убирает обрамляющие пробелы;
2. снимает парные кавычки (`'...'` или `"..."`);
3. `lower()` — приводит к нижнему регистру.

Если `_normalize_text(s1) == _normalize_text(s2)` → **match без обращения к модели**, `exact_success += 1`.

**Примеры:** `Москва` ↔ `москва`, `'Париж'` ↔ `париж`, `"ТОКИО"` ↔ `токио`.

### Шаг 2. Layer 2a — «опечатки» (Levenshtein, без модели)

Считаем `lev_ratio(s1, s2)` — нормализованное расстояние в `[0, 1]` через `difflib.SequenceMatcher`. `0.0` — строки идентичны, `1.0` — максимально разные.

Если `lev_ratio ≤ lev_typo_max` (по умолчанию `0.20`) → **match без обращения к модели**, `typo_success += 1`.

**Примеры:**
- `Масква` ↔ `москва`: lev = 0.17 → match.
- `Москве` ↔ `москва`: lev = 0.17 → match.
- `Париже` ↔ `париж`: lev = 0.09 → match.

**Почему без модели:** если строки почти совпадают по символам, эмбеддинг избыточен и может ошибиться (особенно квантованные модели). Порог `0.20` эмпирически подобран так, чтобы ловить типичные опечатки, но не склеивать разные короткие слова (`кот` vs `код` дают lev = 0.33).

### Шаг 3. Layer 3 — hard match (модель, cos ≥ threshold)

Только теперь вызывается модель:

- `_embed(s1)`, `_embed(s2)` — получаем эмбеддинги (с префиксом, см. §4);
- `cos = cosine(v1, v2)`;
- если `cos ≥ threshold` (по умолчанию `0.82` или `0.75` в demo) → **match**, `embedding_success += 1`.

**Примеры:** `Moscow` ↔ `москва`, `Beijing` ↔ `пекин`, `Moscow` ↔ `москва`.

### Шаг 4. Layer 2b — soft-коридор (модель + Levenshtein)

Если `cos` ниже `threshold`, но попадает в коридор `[soft_cos_min, threshold)` **и** `lev_ratio ≤ lev_max` → **match**, `soft_success += 1`.

По умолчанию `soft_cos_min = 0.55`, `lev_max = 0.35`. Слой нужен для пар, где модель «сомневается», но строки лексически близки. На реальных данных срабатывает редко.

### Шаг 5. Отказ

Если ни одно условие не выполнено → `None`, `failures += 1`.

### Итог

| Layer | Модель | Типичное время | Что ловит |
|---|---|---|---|
| 1 | нет | ~0 мс | регистр, кавычки |
| 2a | нет | ~0.01 мс | опечатки, падежи |
| 3 | да | 50–500 мс | кросс-язык, синонимы |
| 2b | да | 50–500 мс | сомнительные пары |

**Ключевой момент:** для пар с `lev_ratio ≤ lev_typo_max` модель **не вызывается вообще**. Это делает Layer 2a не только точнее, но и в десятки раз быстрее.

## 4. Backend'ы: Ollama и sentence-transformers

Обе реализации возвращают `Callable[[str], np.ndarray]` и полностью взаимозаменяемы. Выбор через параметр `backend`:

### Backend `st` (рекомендуется)

Через `sentence_transformers.SentenceTransformer`. Даёт **корректные эмбеддинги** без GGUF-квантизации, поддерживает префиксы, локальные пути, GPU.

**Плюсы:**
- Правильные эмбеддинги для E5, BGE, nomic и др.
- Полный контроль над пулингом (mean/CLS).
- Батч-энкодинг.

**Минусы:**
- Тянет `torch` (~800 MB – 2 GB).
- Каждый Python-процесс грузит свою копию модели.

### Backend `ollama`

Через `langchain_ollama.OllamaEmbeddings`. Работает через HTTP-сервис Ollama.

**Плюсы:**
- Не требует `torch`.
- Одна копия модели на все процессы.
- Уже может быть в инфраструктуре.

**Минусы:**
- **GGUF-квантизация сжимает cos-диапазон.** Модели вроде E5 дают 0.85–0.95 для **всех** пар, включая разные. Это известная проблема, см. §11.
- Нет прямого контроля над пулингом.

### Когда что использовать

| Ситуация | Backend |
|---|---|
| Семантическая унификация для production | **`st`** |
| Уже есть Ollama для LLM | `ollama` (с оговорками) |
| Нельзя ставить torch (Docker, exe) | `ollama` |
| Нужна максимальная точность | **`st`** |

### Backend `ollama` — установка

```bash
ollama pull paraphrase-multilingual:latest
ollama pull nomic-embed-text-v2-moe:latest
ollama pull bge-m3:567m
```

### Префиксы моделей

Некоторые модели **обучены с префиксами** и работают хуже без них:

| Модель | Префикс |
|---|---|
| `intfloat/multilingual-e5-*` | `query: ` |
| `nomic-embed-text-*` | `search_query: ` |
| `paraphrase-multilingual-*` | (нет) |
| `BAAI/bge-m3` | (нет) |

Префикс определяется автоматически по имени модели (`detect_text_prefix`). Применяется **внутри `_embed`**, после нормализации. Это значит:

- ключ кэша содержит префикс — `Москва` и `москва` дают один и тот же ключ, но `query: москва` отличается от просто `москва`;
- `lev_ratio` считается по строкам **без префикса** — `Масква` vs `москва` даёт lev = 0.17, а не «lev с учётом префикса».

Переопределить префикс можно явно: `semantic_on(..., text_prefix="query: ")` или через env `PROLOG_SEMANTIC_PREFIX`.

## 6. Использование из Prolog

### Директивы (в тексте программы)

```prolog
% Включить с параметрами по умолчанию
:- semantic_on.

% Включить с явным порогом
:- semantic_on(0.80).

% Изменить порог у уже включённого унификатора
:- semantic_threshold(0.70).

% Отключить
:- semantic_off.
```

Директивы обрабатываются `Solver._apply_directives`. Они применяются **после** загрузки базы знаний, но **до** первого запроса.

### Предикаты (можно вызывать в запросах)

```prolog
?- semantic_on.
?- semantic_on(0.75).
?- semantic_status(X).
X = on(0.75).
?- semantic_threshold(0.80).
?- semantic_off.
```

Зарегистрированы в `predicates.py`:
- `semantic_on/0`, `semantic_on/1` — включить;
- `semantic_off/0` — отключить;
- `semantic_threshold/1` — изменить порог;
- `semantic_status/1` — получить статус.

### Полный пример

```prolog
:- semantic_on(0.75).

страна(россия, европа, 144).
страна(япония, азия, 125).

столица(россия, москва).
столица(япония, токио).

% Запрос 1: точное совпадение
?- столица(россия, москва).
true.

% Запрос 2: другой регистр — Layer 1
?- столица(россия, 'Москва').
true.

% Запрос 3: другой падеж — Layer 2a
?- столица(россия, 'Москве').
true.

% Запрос 4: кросс-язык — Layer 3
?- столица(россия, 'Moscow').
true.

% Запрос 5: негатив — должен отвергаться
?- столица(россия, 'Лондон').
false.
```

## 7. Использование из Python

### Минимальный пример

```python
from prolog.solver import Solver
import prolog.embedding_unify as eu

program = """
страна(россия, европа, 144).
страна(япония, азия, 125).
столица(россия, москва).
столица(япония, токио).
"""

solver = Solver(program)

# Отключаем семантику
eu.semantic_off()
print(list(solver.database.query(
    __import__('prolog.parser', fromlist=['Parser']).Parser("столица(россия, 'Москва').").parse_query()
)))
# []

# Включаем
eu.semantic_on(
    model="D:/hf_embedding/paraphrase-multilingual-mpnet",
    backend="st",
    threshold=0.75,
    local_dir="d:/hf_embedding",
    local_files_only=True,
)

# Теперь работает
print(list(solver.database.query(
    __import__('prolog.parser', fromlist=['Parser']).Parser("столица(россия, 'Москва').").parse_query()
)))
# [столица(россия, москва)]
```

### Все параметры `semantic_on`

```python
eu.semantic_on(
    threshold=0.75,              # hard-порог cos
    model="sentence-transformers/paraphrase-multilingual-mpnet-base-v2",
    backend="st",                # 'st' или 'ollama'
    text_prefix=None,            # None=авто, ""=без, "query: "=явный
    soft_cos_min=0.55,           # нижняя граница soft-коридора
    lev_max=0.35,                # макс. lev_ratio в soft-коридоре
    lev_typo_max=0.20,           # порог «опечаток» (Layer 2a)
    max_cache=10000,             # размер кэша эмбеддингов

    # Только для backend='st':
    local_dir="d:/hf_embedding",
    st_cache_folder=None,
    st_device=None,              # 'cpu', 'cuda', 'cuda:0'
    st_local_files_only=True,
    st_verbose=False,            # печатать путь к модели и прогресс-бары

    # Только для backend='ollama':
    base_url="http://localhost:11434",

    force_reload=False,          # пересоздать унификатор (сбросить кэш)
)
```

### Динамическое изменение параметров

```python
eu.semantic_set_threshold(0.80)
eu.semantic_set_corridor(soft_cos_min=0.50, lev_max=0.30, lev_typo_max=0.15)
eu.semantic_set_prefix("query: ")  # сбрасывает кэш
eu.semantic_off()
```

### Получение статуса

```python
u = eu.semantic_get_unifier()
if u is not None:
    print(u.backend)         # 'st' или 'ollama'
    print(u.threshold)       # 0.75
    print(u.lev_typo_max)    # 0.20
    print(u.text_prefix)     # 'query: ' или ''
    print(u.stats)           # {'calls': ..., 'exact_success': ..., ...}
    print(u.cache.stats())   # {'size': ..., 'hits': ..., 'hit_rate': ...}
```

## 8. Выбор модели

Сравнение моделей на реальном тестовом наборе (14 запросов о странах и столицах):

| Модель | Backend | Побед | `failures` | `кошка↔собака` | Комментарий |
|---|---|---|---|---|---|
| `paraphrase-multilingual-mpnet` | st | **10–11** | 78 | 0.43 | ✅ Рекомендуется |
| `paraphrase-multilingual-MiniLM` | st | 10 | 78 | 0.43 | ✅ Компактнее |
| `paraphrase-multilingual` | ollama | 10 | 78 | 0.43 | ✅ Лёгкий вариант |
| `nomic-embed-text-v2-moe` | ollama | 9 | 82 | 0.48 | ✅ Работает |
| `bge-m3` | ollama | 12 | 76 | **0.79** | ⚠️ Ложные срабатывания |
| `intfloat/multilingual-e5-large` | st | 13 | **0** | **0.90** | ❌ Сжатый cos-диапазон |
| `qllama/multilingual-e5-large` | ollama | 14 | **0** | **0.90** | ❌ Сломан квантизацией |

**Ключевой вывод:** количество «побед» **не показатель качества**. Сломанные модели выигрывают больше, потому что соглашаются со всем подряд. Смотрите на:

1. **`failures > 0`** — унификатор умеет отказывать.
2. **cos негативных пар** (`кошка↔собака`, `лондон↔москва`) — должны быть < 0.6.
3. **NEGATIVE-запросы** — должны **проваливаться**.

### Рекомендации по выбору

| Задача | Модель |
|---|---|
| Универсальная семантическая унификация (RU+EN) | **`paraphrase-multilingual-mpnet-base-v2`** |
| Компактность важнее качества | `paraphrase-multilingual-MiniLM-L12-v2` |
| Много кросс-язычных пар с редкими языками | `bge-m3` (с осторожностью) |
| Только русский, домен технический | `rubert-tiny2` или другая русская модель |
| Уже есть Ollama | `paraphrase-multilingual:latest` |

**Не используйте** `multilingual-e5-*` для семантической унификации. Модель обучена с низкой температурой и сжимает cos в узкий диапазон — абсолютный порог не работает. См. §11.

## 9. Тонкая настройка порогов

Все пороги можно менять через env, код или Prolog.

### `threshold` (hard-порог cos)

- **Высокий** (0.85+): только очень уверенные совпадения. Много пропусков, мало ложных.
- **Средний** (0.75): баланс. Рекомендуется для paraphrase-multilingual.
- **Низкий** (0.65): ловит больше, но растёт риск ложных.

**Как подобрать:** постройте таблицу косинусов на парах «правильных» и «неправильных» совпадений. Порог = середина между `min(positive)` и `max(negative)`. Если эти значения пересекаются — модель плохо подходит, смените её.

### `lev_typo_max` (порог опечаток, Layer 2a)

- **0.15**: только совсем мелкие опечатки (1–2 символа в коротком слове).
- **0.20** (по умолчанию): компромисс.
- **0.30**: агрессивно; `кот` vs `код` начнёт совпадать.

**Осторожно:** слишком высокий порог склеивает разные короткие слова.

### `soft_cos_min` и `lev_max` (Layer 2b)

Работают вместе: match, если `soft_cos_min ≤ cos < threshold` **и** `lev_ratio ≤ lev_max`.

- `soft_cos_min = 0.55`, `lev_max = 0.35` — консервативно.
- `soft_cos_min = 0.50`, `lev_max = 0.30` — чуть либеральнее.

В большинстве случаев этот слой почти не срабатывает. Оставьте значения по умолчанию, если нет конкретной задачи.

## 10. Производительность и кэш

### Что кэшируется

Кэш эмбеддингов — `EmbeddingCache`. Ключ: нормализованная строка **с префиксом**. Значение: `np.ndarray(float32)`.

- **Hit rate на типичных данных:** 70–80%. Много повторяющихся атомов (имена предикатов, константы).
- **Размер по умолчанию:** 10 000 записей. При переполнении удаляется ~10% самых старых (FIFO).

### Что **не** кэшируется

- Кэш **не учитывает** `depth` — это правильно, эмбеддинг не зависит от глубины.
- При смене префикса (`semantic_set_prefix`) кэш **очищается** — старые ключи становятся невалидными.

### Стоимость слоёв

| Layer | Стоимость | Доля в типичном прогоне |
|---|---|---|
| 1 (exact) | ~0 мс | 5–10% матчей |
| 2a (typo) | ~0.01 мс | 15–25% матчей |
| 3 (hard) | 50–500 мс | 60–80% матчей |
| 2b (soft) | 50–500 мс | <2% матчей |

**Главный выигрыш:** Layer 2a делает так, что опечатки и падежи обрабатываются **без модели**. Это экономит не только время, но и вызовы к Ollama/HF.

### Cold start

- Backend `st`: 2–5 секунд на первую загрузку модели.
- Backend `ollama`: 2–3 секунды (cold start Ollama).

Чтобы прогреть заранее:

```python
# Для st
import prolog.embedding_unify as eu
eu.semantic_on(backend='st', model='...', local_dir='...')
# Первый запрос прогреет модель
```

Или через переменную окружения `PROLOG_ST_VERBOSE=1`, чтобы видеть прогресс.

### Оптимизация для production

1. **Используйте `st` backend с `local_files_only=True`** — не будет сетевых задержек.
2. **Предзагружайте модель при старте приложения** — первый запрос не должен «залипать».
3. **Увеличьте `max_cache`** до 50 000–100 000, если база знаний большая.
4. **Для GPU:** `st_device='cuda'` даёт 10–20× ускорение на энкодинге.

## 11. Диагностика и troubleshooting

### Проблема 1: всё совпадает со всем (`failures = 0`, NEGATIVE проходят)

**Симптомы:**
- В статистике `failures = 0`.
- Негативные пары (`кошка↔собака`, `лондон↔москва`) дают cos > 0.8.
- Запросы возвращают много решений вместо одного.

**Причина:** модель коллапсировала эмбеддинги в узкий конус. Типично для:
- квантованных моделей (GGUF Q4/Q5) — например, `qllama/multilingual-e5-large`;
- E5 без префикса `query: `;
- неправильного пулинга (CLS вместо mean).

**Диагностика.** Запустите sanity-check:

```python
from sentence_transformers import SentenceTransformer
import numpy as np

m = SentenceTransformer("D:/hf_embedding/paraphrase-multilingual-mpnet")

def cos(a, b):
    va = m.encode(a, normalize_embeddings=True)
    vb = m.encode(b, normalize_embeddings=True)
    return float(np.dot(va, vb))

print(f"Москва ↔ Москве:     {cos('москва', 'Москве'):.4f}  (ожидание: >0.9)")
print(f"Moscow ↔ москва:     {cos('Moscow', 'москва'):.4f}  (ожидание: >0.8)")
print(f"кошка  ↔ собака:     {cos('кошка', 'собака'):.4f}   (ожидание: <0.6)")
print(f"лондон ↔ москва:     {cos('лондон', 'москва'):.4f}  (ожидание: <0.5)")
```

Если `кошка↔собака > 0.7` — модель плохая. Смените на `paraphrase-multilingual-mpnet`.

**Решение:**
1. Для Ollama E5 — перейти на `sentence_transformers` (см. §5).
2. Для E5 через `st` — убедиться, что префикс `query: ` применяется (см. §4).
3. Проверить `1_Pooling/config.json` — должно быть `pooling_mode_mean_tokens: true`.

### Проблема 2: `[ST] resolved model path: ...` и прогресс-бары

**Симптомы:**
```
[ST] resolved model path: 'D:/hf_embedding/paraphrase-multilingual-mpnet'
Loading weights: 100%|████████| 199/199 [00:00<00:00, 4702.06it/s]
```

**Решение:** по умолчанию они **не появляются**. Если появились — установите `PROLOG_ST_VERBOSE=0` или передайте `st_verbose=False` в `semantic_on`.

### Проблема 3: `RepositoryNotFoundError`

**Симптомы:**
```
Repository Not Found for url: https://huggingface.co/sentence-transformers/multilingual-e5-large/...
```

**Причина:** модель задана как `multilingual-e5-large` без организации. `sentence-transformers` подставляет `sentence-transformers/` как org, а такой модели на HF нет. Правильный ID — `intfloat/multilingual-e5-large`.

**Решение:** используйте полный HF ID или короткие алиасы (`resolve_model_id` их автоматически раскрывает):

```python
eu.semantic_on(model="multilingual-e5-large")  # → intfloat/multilingual-e5-large
eu.semantic_on(model="paraphrase-multilingual-mpnet")  # → sentence-transformers/paraphrase-multilingual-mpnet-base-v2
eu.semantic_on(model="bge-m3")  # → BAAI/bge-m3
```

### Проблема 4: Медленно

**Возможные причины:**
1. **Cold start** — модель грузится в память при первом запросе. Прогрейте.
2. **Модель на CPU** — `st_device='cpu'` явно или нет GPU.
3. **Много hard-матчей** — каждый вызывает модель. Проверьте `st['embedding_success']`.
4. **Кэш переполнен** — увеличьте `max_cache`.
5. **Ollama cold start** — прогрейте её пустым запросом.

### Проблема 5: падежи и опечатки не ловятся

**Симптомы:** `Москве`, `Масква`, `Париже` не совпадают.

**Причина:** `lev_typo_max` слишком маленький или модель не вызывается.

**Решение:** проверьте `u.lev_typo_max` — по умолчанию `0.20`. Для пар `Москве↔москва` (lev = 0.17) этого достаточно. Если не работает — увеличьте до `0.22`:

```python
eu.semantic_on(lev_typo_max=0.22)
```

### Как читать статистику

```
Всего вызовов унификации:      123
Успешно строго:                25    ← strict unify
Успешно exact (нормализация):  5     ← Layer 1
Успешно typo (опечатки/падежи):3     ← Layer 2a
Успешно hard (cos >= порог):   13    ← Layer 3
Успешно soft (Levenshtein):    1     ← Layer 2b
Провалов:                      76    ← отказы
```

**Здоровые значения:**
- `exact + typo > 0` — работает Layer 1/2a.
- `hard > 0` и `hard < calls` — модель что-то находит, но не всё.
- `failures > 0` — унификатор умеет отказывать.
- `soft ≈ 0` — нормально, слой срабатывает редко.

**Плохие значения:**
- `failures = 0` — модель сломана (всё проходит).
- `exact + typo = 0` при наличии падежей/регистра — Layer 1/2a не работают.
- `hard = 0` — модель ничего не находит (проверьте префикс).

## 12. Примеры

### Пример 1: обработка пользовательского запроса

```python
from prolog.solver import Solver
import prolog.embedding_unify as eu

program = """
столица(россия, москва).
столица(франция, париж).
столица(китай, пекин).
"""

# Включаем семантику
eu.semantic_on(
    backend='st',
    model='D:/hf_embedding/paraphrase-multilingual-mpnet',
    local_dir='d:/hf_embedding',
    local_files_only=True,
    threshold=0.75,
)

solver = Solver(program)

# Пользователь пишет свободно
for question in [
    "столица(россия, москва).",       # точное
    "столица(россия, 'Москва').",     # регистр
    "столица(россия, 'Москве').",     # падеж
    "столица(россия, 'Moscow').",     # кросс-язык
    "столица(россия, 'Лондон').",     # негатив
]:
    result = solver.find_solutions(question)
    print(f"{question:<35} → {result}")
```

Вывод:
```
столица(россия, москва).         → [{'X': 'москва'}]
столица(россия, 'Москва').       → [{'X': 'москва'}]
столица(россия, 'Москве').       → [{'X': 'москва'}]
столица(россия, 'Moscow').       → [{'X': 'москва'}]
столица(россия, 'Лондон').       → False
```

### Пример 2: глоссарий для аббревиатур (на уровне Prolog)

Аббревиатуры — **не задача** семантической унификации. Это знание о мире. Решается через обычный Prolog-глоссарий:

```prolog
% Глоссарий — обычные факты
синоним(рф, россия).
синоним(российская_федерация, россия).
синоним(сша, соединённые_штаты).
синоним(фрг, германия).

% Расширение предикатов через синонимы
столица(X, Y) :- синоним(X, X2), столица(X2, Y), X \= X2.
столица(X, Y) :- синоним(Y, Y2), столица(X, Y2), Y \= Y2.

% Теперь работает
?- столица('РФ', X).
X = москва.
```

Такой подход **универсален** — глоссарий расширяется без правки кода.

### Пример 3: сравнение моделей

```python
import prolog.embedding_unify as eu
from prolog.solver import Solver

PROGRAM = """
страна(россия, европа, 144).
столица(россия, москва).
"""

MODELS = [
    ("paraphrase-multilingual-mpnet", "st",
     "D:/hf_embedding/paraphrase-multilingual-mpnet"),
    ("multilingual-e5-large", "st",
     "D:/hf_embedding/multilingual-e5-large"),
]

for name, backend, path in MODELS:
    print(f"\n=== {name} ===")
    eu.semantic_off()
    eu.semantic_on(
        backend=backend, model=path, local_dir="d:/hf_embedding",
        local_files_only=True, threshold=0.75,
    )
    solver = Solver(PROGRAM)
    for q in ["столица(россия, 'Москве').", "столица(россия, 'Лондон')."]:
        result = solver.find_solutions(q)
        print(f"  {q:<35} → {result}")

    u = eu.semantic_get_unifier()
    print(f"  stats: {u.stats}")
```

## Резюме

- **Семантическая унификация** — opt-in надстройка над строгой. Включается директивой `:- semantic_on.` или вызовом `semantic_on()`.
- **Три слоя** работают последовательно: нормализация (регистр/кавычки) → Levenshtein (опечатки/падежи, без модели) → эмбеддинги (кросс-язык, синонимы).
- **Backend `st`** рекомендуется для production; **`ollama`** — fallback, если нельзя ставить torch.
- **Модель `paraphrase-multilingual-mpnet`** — лучший выбор для RU+EN.
- **Не используйте E5** для семантической унификации — сжатый cos-диапазон делает пороговую фильтрацию невозможной.
- **Аббревиатуры и факты о мире** решаются глоссарием на уровне Prolog, а не в embedding-слое.
- **Проверяйте `failures > 0`** — если унификатор никогда не отказывает, он сломан.
